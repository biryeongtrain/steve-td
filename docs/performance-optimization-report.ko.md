# 성능 최적화: 경기 부하 측정과 결과

실제 경기와 비슷한 부하에서 서버 틱 시간을 재고, 시간이 많이 드는 곳을 spark로 찾아 고친 기록이다. 최적화 전 소스로 띄운 대조 서버와 최적화 서버에 같은 테스트를 돌려 비교했다.

## 요약

| 부하 | 지표 | 대조 서버 | 최적화 서버 | 변화 |
|---|---|---:|---:|---:|
| 보통 라운드 | 평균 틱 시간 | 6.15 ms | 3.78 ms | -38.6% |
| 보통 라운드 | p95 틱 시간 | 15.38 ms | 9.90 ms | -35.6% |
| 과부하 라운드 | 평균 틱 시간 | 19.67 ms | 11.08 ms | -43.7% |
| 과부하 라운드 | p95 틱 시간 | 28.97 ms | 17.54 ms | -39.5% |

- 보통 라운드는 5대5, 타워 230기, 16라운드 자연 웨이브(몬스터 최대 약 450마리)다.
- 과부하 라운드는 같은 보드에 25라운드 자연 웨이브와 라인당 인컴 30마리를 더한 것이다(몬스터 최대 약 970마리).
- 전투 배속을 켠 서버는 평균 틱 시간이 20 ms 이하일 때 40 TPS로 올리고 25 ms를 넘으면 20 TPS로 되돌린다(`CombatSpeedConfig` 기본값). 과부하 라운드에서 대조 서버는 이 경계에 걸리고 최적화 서버는 그 아래에 있다.
- 타워와 몬스터의 판정 결과는 바꾸지 않았다. 달라질 수 있는 곳은 [바꾼 것](#바꾼-것)의 항목마다 적었다.

## 측정 방법

측정은 `GameMatchPerformanceTest`가 한다. 평소 검증에서는 아무것도 하지 않고, 켰을 때만 돈다.

| 항목 | 내용 |
|---|---|
| 경기 | 운영 맵 템플릿을 격리된 GameTest 월드에 놓고 `SemionGame`을 5대5로 시작한다 |
| 빌더 | 주민, 동물, 언데드, 흑마법사, 무리, 네더, 엔드, 바다, 고대 도시, 마도사 |
| 보드 | 플레이어마다 타워 한도를 끝까지 사고 실제 구매·업그레이드 API로 23기를 채운다. 합계 230기 |
| 증강 | 플레이어마다 2장을 고정해 넣는다(세 묶음을 돌려 쓴다) |
| 웨이브 | 번들 기본 설정에 시즌 3 수량 배율을 켠 것. 20라운드부터는 `overworld_assault` 템플릿으로 고정한다 |
| 보통 라운드 | 16라운드 자연 웨이브. 600틱이 끝날 때 타워 약 147기가 살아 있다 |
| 과부하 라운드 | 25라운드 자연 웨이브에 라인당 인컴 30마리(상점의 모든 종류를 돌려 가며). 250틱쯤 모든 라인이 뚫리고 보스 앞 최종 방어로 넘어간다 |
| 측정 구간 | 측정 라운드 앞의 두 라운드를 예열로 돌린 뒤, 웨이브 시작부터 600틱 |
| 서버 | Minecraft 26.3, Java 25.0.4, G1, 힙 4 GiB 고정, `-XX:ActiveProcessorCount=4` |
| 장비 | Ryzen 7 7800X3D, Windows 11 |
| 대조 서버 | 커밋 `f5377dde`의 실제 코드에 같은 테스트만 더한 것 |
| 반복 | 서버와 부하마다 새 JVM으로 5회. 대조와 최적화를 번갈아 돌렸다. 표의 값은 5회의 중앙값이다 |
| spark | 1.10.187(Fabric). 백그라운드 프로파일러는 끈다 |

- 틱 시간은 프로파일러 없이 쟀다. 서버가 기록한 틱별 시간(`MinecraftServer.getTickTimesNanos`)과 서버 스레드의 CPU 시간·할당량을 쓰고, 끝날 때 `spark tps`를 로그에 남긴다.
- 항목별 비중은 따로 돌린 실행에서 spark 프로파일러(Java 샘플러, 2 ms)로 같은 600틱을 쟀다.
- GameTest 서버는 틱 사이에 쉬지 않는다. 그래서 TPS가 아니라 틱당 시간을 본다.
- 클라이언트는 붙이지 않았다. 운영 서버와 운영 월드는 쓰지 않았다.

## 대조 서버에서 시간이 든 곳

spark 프로파일에서 뽑은 틱당 시간이다(ms).

| 항목 | 보통 라운드 | 과부하 라운드 |
|---|---:|---:|
| 몬스터의 방어 대상 탐색 (`AcquireLaneDefenseTargetGoal`) | 0.26 | 3.80 |
| 바닐라 A* 경로 탐색 (`PathFinder.findPath`) | 0.89 | 2.32 |
| 동물 빌더의 무리 상태 갱신 (`AnimalStackTower.refreshAnimalStacks`) | 1.37 | 1.38 |
| 증강 보유 확인 (`AugmentSnapshot.has`) | 0.78 | 0.65 |
| 주민 타워 판별 (`VillagerTowers.isAdvVillagerTower`) | 0.15 | 0.08 |
| 바닐라 이동과 충돌 (`Entity.move`) | 1.14 | 4.55 |
| 평균 틱 시간 (프로파일 실행) | 6.26 | 18.86 |

동물 빌더는 열 명 중 한 명인데 보통 라운드 틱의 22%를 썼다. 과부하 라운드는 몬스터 엔티티 틱이 전체의 77%였고, 방어 대상 탐색과 경로 탐색이 전체의 32%였다.

## 바꾼 것

### 1. 동물 빌더의 무리 상태 갱신

- 문제: 동물 타워는 틱마다 라인 전체의 무리 수와 우두머리 오라를 다시 계산했다. 타워마다 한 번씩, 계산마다 라인을 여러 번 훑어서 타워 수의 세제곱에 가까웠다.
- 변경: 계산에 들어가는 값이 직전 계산 때와 같으면 건너뛴다. 보는 값은 라인의 타워 구성(`PlayerLane.towerRevision`), 동물 타워마다의 생존 여부·위치·증강·타워 종류, 밸런스 설정이다. 하나라도 바뀌면 예전 계산을 그대로 한다.
- 동작: 같다. 값이 바뀐 직후의 틱에 반영되는 순서도 그대로다.
- 테스트: `AnimalTowerRefreshOrderingTest`에 건너뛰는 경우와 밸런스 재적용을 더했다.

### 2. 증강 보유 확인

- 문제: 타워의 최대 체력과 피해 계산이 틱마다 수천 번 묻는데, 물을 때마다 스트림과 문자열을 새로 만들었다.
- 변경: 반복문으로 바꾸고, ID를 견줄 때 문자열을 만들지 않는다(`AugmentSnapshot.has`, `AugmentCatalog.matchesSelection`, `AugmentCombat.beneficialBonus`).
- 동작: 같다.
- 테스트: `AugmentCatalogLookupTest`가 모든 카드 ID 조합을 예전 식과 견준다.

### 3. 몬스터의 방어 대상 탐색

- 문제: 표적이 없는 몬스터가 2틱마다 라인 전체 범위의 엔티티를 훑었다. 실제로 고를 수 있는 대상은 추적 거리(8칸 또는 공격 사거리) 안에만 있다. 마왕이 없는 경기에서도 마왕을 찾느라 한 번 더 훑었다. 몬스터가 한곳에 몰리면 몬스터 수의 제곱으로 늘었다.
- 변경: 훑는 범위를 몬스터 주변(추적 거리 + 1칸)으로 줄였다. 지배당한 몬스터가 없으면 타워 엔티티만 본다. 마왕 상태가 하나도 없으면 마왕 탐색을 건너뛰고, 있으면 월드의 플레이어 목록에서 찾는다.
- 동작: 같다. 후보와 순서가 예전과 같아서 같은 거리의 대상 중 고르는 쪽도 같다. 마왕 둘이 정확히 같은 거리에 있을 때만 고르는 쪽이 달라질 수 있다.
- 테스트: `MonsterDefenseTargetScanTest`가 2,401개 위치에서 예전 방식의 결과와 견준다(지배당한 몬스터가 있을 때와 없을 때).

### 4. 경로 탐색

- 문제: 근접 몬스터의 경로 탐색 거리는 5칸이다. 50칸 떨어진 경로점까지 걷는 동안 4칸마다 바닐라 A*를 다시 돌렸다. 타워도 움직이는 몬스터를 쫓을 때 대상이 칸을 넘을 때마다 A*를 돌렸다.
- 변경: 목표까지 직선 위의 칸이 모두 걸을 수 있는 칸이면 A* 없이 그 직선을 경로로 쓴다(`EntityGoalStraightPath`). 한 번에 만드는 길이와 목표 한 칸 앞에서 끝나는 규칙은 바닐라와 같다. 직선 위에 벽·구멍·위험 블록이 있거나 땅에 서 있지 않으면 바닐라 경로 탐색을 그대로 쓴다.
- 쓰는 곳: 몬스터의 라인 이동(`LaneFollowGoal`), 몬스터의 대상 접근(`MonsterAttackTargetGoal`), 타워의 추격(`SemionTowerEntity.moveToward`).
- 동작: 가는 곳과 속도는 같다. 비스듬히 출발할 때 중간에 밟는 칸이 A*가 고르던 칸과 한 칸 안에서 다를 수 있다.
- 테스트: `EntityGoalStraightPathTest`(직선, 벽, 바닥 구멍, 경로 재사용, 공중).

### 5. 주민 타워 판별

- 문제: 모든 타워의 사거리 계산이 "고급 주민 타워인가"를 묻는데, 물을 때마다 타워 16종 목록을 스트림으로 훑었다.
- 변경: ID 집합에서 찾는다.
- 동작: 같다.

### 6. 타워의 공격 후보 수집

- 변경: 범위 안의 엔티티 전체가 아니라 몬스터 엔티티만 훑는다(`TowerAttackMonsterGoal`). 후보와 순서는 같다.

## 남은 비용과 한계

- 최적화 뒤 과부하 라운드 틱의 60%쯤은 바닐라의 이동·충돌·밀어내기다(`Entity.move` 5.2 ms, `LivingEntity.pushEntities` 1.0 ms, `Entity.applyEffectsFromBlocks` 1.0 ms). 몬스터끼리 밀어내기나 충돌 판정을 줄이면 더 내려가지만 몬스터가 겹쳐 서는 등 게임 모습이 달라진다. 그래서 손대지 않았다.
- 클라이언트가 없다. 패킷 전송, VFX, HUD 비용은 재지 않았다.
- 엔티티 AI의 난수는 고정하지 않았다. 실행마다 전투 경과가 조금씩 다르다.
- 보드는 테스트가 한 번에 사서 올린 것이다. 앞 라운드에서 쌓인 성장은 없다. 설정은 번들 기본값이고 웨이브 템플릿은 하나다.
- 한 장비에서 서버마다 5회 쟀다.

## 다시 재는 법

spark의 26.3용 Fabric JAR 경로를 넣는다. 결과는 로그의 `MATCH_PROFILE` 한 줄과 격리 실행 폴더의 `match-profile-<이름>.json`에 남는다. 실행 폴더는 로그의 `Isolated 26.3 GameTest directory`에 찍힌다.

```powershell
.\gradlew.bat runGameTest --offline --console=plain --no-daemon "-Psemiontd.matchProfile=true" "-Psemiontd.profileVariant=optimized" "-Psemiontd.matchSpark=tps" "-Psemiontd.sparkJar=<spark JAR 경로>"
```

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `semiontd.matchRound` | 16 | 측정할 라운드 |
| `semiontd.matchSummons` | 0 | 라인마다 넣을 인컴 수 |
| `semiontd.matchTicks` | 600 | 측정 틱 수 |
| `semiontd.matchSpark` | off | `tps`는 끝에 `spark tps`를 찍고, `profile`은 측정 구간을 프로파일해 실행 폴더의 `config/spark/`에 `.sparkprofile`을 남긴다 |
| `semiontd.matchBuilders` | 위의 10종 | 쉼표로 나눈 빌더 ID 10개 |
| `semiontd.profileVariant` | unspecified | 결과 파일 이름에 붙는 이름 |

과부하 라운드는 `"-Psemiontd.matchRound=25" "-Psemiontd.matchSummons=30"`을 더한다.

대조 서버는 비교할 커밋을 다른 폴더에 꺼내고(`git worktree add`), 그 폴더에 `GameMatchPerformanceTest.java`, GameTest `fabric.mod.json`의 등록 한 줄, `build.gradle`의 `semiontd.matchProfile` 블록, `libs/`를 옮긴 뒤 같은 명령을 돌린다.
