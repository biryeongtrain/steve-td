# 라이브 밸런스 대시보드와 내부 API 기획안

작성일: 2026-09-22

검토 기준: 게임 `s3-release`의 `d35a4b35`, 웹 `codex/s3-release`의 `13c80104`

상태: 게임 관리 API, 웹 편집기와 인증을 구현하고 로컬 통합 검증을 마쳤다. 초기 편집 범위는 4,273개 항목이며, 검증하지 않은 4,019개 항목은 읽기 전용이다. 운영 설정 변경과 배포는 수행하지 않았다. [검증 결과와 남은 제한](2026-09-23-live-balance-dashboard-validation.ko.md)을 함께 확인한다.

후속 상태: 사용자 승인으로 2026-09-23 게임·웹 운영 배포를 마쳤다. [배포 기록](2026-09-23-live-balance-dashboard-deployment.ko.md)을 기준으로 현재 운영 상태를 확인한다. 아래 미배포 언급은 최초 구현 범위의 기록이다.

## 1. 결론

구현할 수 있다. 운영자는 웹에서 수치를 찾고 수정하며, AI는 개발자가 부여한 권한으로 같은 변경 API를 사용한다. 수정한 값을 확인하려고 서버를 재시작할 필요는 없다.

다만 **진행 중인 경기까지 적용하는 시점은 항목마다 구분해야 한다.** 현재 타워 수치는 실행 중에 갱신할 수 있지만, 증강과 웨이브는 경기 시작 때 고정한다. 이 차이를 무시하고 파일 저장과 전체 재적용만 연결하면 화면의 수치와 실제 효과가 달라질 수 있다.

이 문서의 기본안은 다음과 같다.

- 웹 편집과 AI 요청을 하나의 검증·적용 경로로 연결한다.
- 검증한 항목은 즉시 적용하고, 나머지는 다음 준비 단계 또는 다음 경기로 예약한다.
- 저장된 초안, 예약된 변경, 실제 적용값을 화면에서 구분한다.
- 운영자는 변경 전후 값과 적용 범위를 확인하고, 이전 수치로 되돌릴 수 있다.

여기서 ‘즉시’는 요청을 받은 게임 서버가 다음 적용 가능한 서버 틱에 변경하는 것을 뜻한다. 네트워크 지연이나 서버 정지 상태에서의 완료 시간을 보장한다는 뜻은 아니다. 적용 완료 여부는 게임 서버의 응답으로 확인한다.

## 2. 현재 구조에서 확인한 것

| 항목 | 현재 구현 | 필요한 작업 |
|---|---|---|
| 타워 수치 | `TowerBalanceRuntime`이 전역 설정을 사용하며, 기존 타워의 타입을 갱신하는 경로가 있음 | 변경 항목별 안전성 검사와 전용 적용 경로 |
| 증강 | 참가자 구성이 확정된 경기에는 새 `AugmentConfig`를 넣지 않음 | 다음 경기 예약. 진행 중인 경기 변경은 별도 설계 필요 |
| 웨이브 | 경기 시작 이후 `applyConfigs`가 웨이브 설정을 교체하지 않음 | 다음 경기 예약. 이미 정한 편성과 보상 유지 |
| 설정 재적용 | `/semiontd reload`가 밸런스 외 설정과 저장 서비스까지 다시 구성함 | 밸런스만 바꾸는 메서드 분리 |
| 웹 | Next.js, PostgreSQL 기반 조회 사이트. 관리자 인증과 변경용 API를 찾지 못함 | 로그인, 권한, 편집 화면, 변경 이력 추가 |
| 동기화 | 게임 카탈로그와 경기 기록을 웹 DB로 가져오며 동기화 루프는 30초 간격 | 편집용 조회와 적용 확인은 게임 서버에 직접 요청 |
| 경기 버전 | 경기 시작 때 `catalogVersion`을 기록함 | 경기 중 패치 이력과 혼합 버전 경기 표시 |

번들 기본 JSON 7종에는 숫자 값이 8,292개 있다. 타워 설정 6,656개, 증강 433개, 웨이브 626개, 인컴 512개, 특성 32개, 경제 28개, 몬스터 시간 경과 성장 5개다. 스키마 번호와 반복 편성의 값도 포함한 단순 집계이며, 편집 가능한 항목 수나 라이브 값의 개수는 아니다.

이 정도 규모에서는 JSON 전체를 보여주는 화면보다 빌더, 타워, 증강 이름으로 찾는 표가 필요하다. 구현 중에 편집 항목과 코드에 고정된 수치도 구분해야 한다.

## 3. 관리 범위

### 편집 대상으로 삼을 설정

| 영역 | 화면에서 다룰 항목 | 초기 적용 정책 |
|---|---|---|
| 타워 기본 스탯 | 체력, 공격력, 사거리, 공격 주기, 어그로 | 검증된 공격력·사거리·어그로는 즉시 허용 후보. 체력·공격 주기는 다음 준비 단계 |
| 타워 비용 | 설치 가격, 승급 경로별 가격 | 다음 준비 단계 |
| 타워 능력 | 회복량, 보호막, 범위, 쿨다운, 성장 계수와 상한 | 기본은 다음 경기. 개별 검증을 통과한 항목만 적용 시점 확대 |
| 공통·직업 증강 | 피해 배율, 충전 수, 회복량, 보상, 발동 간격, 희귀도 확률 | 다음 경기 |
| 특성 | 기존 설정에 있는 효과 수치 | 다음 경기 |
| 인컴 | 가격, 인컴 증가량, 유닛 스탯과 유틸 효과 | 다음 경기 |
| 웨이브 | 라운드별 편성 수, 체력·공격 배율, 회복 유닛 수와 회복량 | 다음 경기 |
| 경제·성장 | 시작 재화, 정기 지급, 생산, 몬스터 시간 경과 성장 | 다음 경기 |

‘즉시 허용 후보’는 현재 코드에 갱신 경로가 있다는 뜻이다. 효과 재계산과 엔티티 검증을 통과하기 전에는 즉시 적용 버튼을 열지 않는다. 같은 `damage` 필드라도 특수 타워가 별도 계산을 하면 적용 정책을 따로 지정한다.

최초 구현에서 제외할 항목은 로그인 정보, DB 연결 정보, 서버 주소, 파일 경로, 레이팅 초기화, 유저 재화 직접 수정, 임의 명령 실행이다. 새 타워나 새 증강 효과를 만드는 기능도 포함하지 않는다. 코드에 없는 능력은 수치 편집만으로 추가할 수 없다.

빌더 활성화, 증강 공개 후보 활성화 등 공개 범위 변경은 일반 수치 편집과 분리한다. 기존 비활성 직업을 대시보드 도입으로 활성화하지 않는다.

## 4. 운영자 화면

관리 화면은 기존 웹의 `/admin/balance`에 둔다. 공개 도감과 경기 통계는 읽기 전용으로 유지한다.

### 4.1 화면 구성

| 위치 | 표시와 조작 | 의미 |
|---|---|---|
| 상단 서버 상태 | 테스트/운영 구분, 서버 ID, 연결 상태, 현재 경기와 라운드, 실제 적용 버전 | 지금 어느 서버의 값을 보고 있는지 확인 |
| 왼쪽 분류 | 타워, 증강, 특성, 인컴, 웨이브, 경제 | 수정할 설정 영역 선택 |
| 검색·필터 | 한글 이름, 내부 ID, 빌더, 티어, 증강 등급, 변경한 항목만 보기 | 수천 개 항목에서 수정 대상을 좁힘 |
| 수치 표 | 항목 이름, 단위, 실제 적용값, 다음 경기 예약값, 수정값, 증감률, 적용 시점 | 저장값과 전투에 사용 중인 값을 혼동하지 않게 함 |
| 상세 패널 | 효과 설명, 값의 의미, 제한 범위, 영향을 받는 타워·증강 | 공유 능력 수치의 영향 범위 확인 |
| 변경 목록 | 변경 전후 값, 사유, 경고, 초안 저장, 검사, 적용 | 여러 수치를 한 번의 패치로 묶음 |
| 변경 이력 | 작업자, 요청 출처, 변경 사유, 결과, 적용 경기·라운드, 되돌리기 | 누가 무엇을 언제 바꿨는지 확인 |

### 4.2 편집 규칙

- 기본 화면은 숫자 입력과 선택 상자로 구성한다. JSON 편집은 개발자용 가져오기·내보내기에만 사용하며 같은 검사를 거친다.
- 비율 `0.2`는 `20%`, 틱은 초와 원래 틱 값을 함께 표시한다. 단위를 키 이름만 보고 추측하지 않는다.
- 여러 항목을 선택해 `+10%`, `-5`, 같은 값 지정 등을 할 수 있다. 적용 전에는 각 항목의 최종 숫자로 펼쳐서 보여준다. API에도 계산식 대신 최종 숫자를 전송한다.
- 정수 개수와 틱 단위는 항목에 정한 반올림 규칙을 사용하고 결과를 미리 보여준다. 음수, 무한대, 나눗셈 불가 값 등은 저장 단계에서 막는다.
- 스탯 변화가 설명에 반영되는 항목은 기존 설명 생성 경로를 재사용한다. 고정 문구여서 자동 반영하지 못하는 설명에는 경고를 표시한다.
- 운영 패치를 입력할 때마다 적용하지 않는다. `검사 → 변경 내용 확인 → 적용`으로 구분한다. 초안 자동 저장은 운영 적용이 아니다.
- 연결이 끊기면 마지막 조회 시각을 표시하고 적용 버튼을 잠근다. 오래된 도감 값을 라이브 값처럼 표시하지 않는다.
- 색상 외에 증감 기호, 단위, 텍스트 상태를 표시한다. 키보드로 표와 입력란을 조작할 수 있어야 한다.

### 4.3 사용 예

운영자가 ‘돼지 타워’를 검색하고 체력을 수정한다. 변경 목록에는 기존 값, 새 값, 증감률과 `다음 준비 단계`가 나온다. 검사를 통과한 뒤 적용하면 `예약됨`으로 표시한다. 게임 서버가 해당 준비 단계에서 실제로 반영한 뒤에만 `적용 완료`로 바뀐다. 방벽을 비롯한 다른 타워의 수치는 초기 버전에서 다음 경기 적용을 사용한다.

같은 목록에 증강 보상도 넣으면 증강은 `다음 경기` 항목이라는 안내가 나온다. 전체를 다음 경기로 예약하거나 두 패치로 나눠야 한다. 시스템이 일부 값만 먼저 적용하지 않는다.

## 5. 공통 구조

```text
운영자 웹 화면 ─┐
               ├─ 웹 관리 API: 인증, 권한, 초안, 요청 이력
개발자 지시 AI ─┘          │
                          └─ 비공개 게임 API
                              검사 → 적용 예약 → 서버 틱에서 반영
                                      │
                                      ├─ 실제 버전과 결과 응답
                                      └─ 카탈로그 내보내기 → 기존 웹 동기화
```

웹과 AI는 같은 API 계약을 사용한다. AI 전용 우회 적용 경로를 만들지 않는다. 웹 프로세스에 게임 폴더 쓰기 권한이나 서버 콘솔 실행 권한을 주지 않는다.

게임 내부에 밸런스 전용 HTTP 처리와 `BalanceChangeService`를 추가한다. HTTP 스레드는 요청 파싱과 인증을 담당하고, 게임 상태 조회·적용은 서버 실행 큐를 거친다. 파일 쓰기와 큰 JSON 직렬화는 틱을 오래 점유하지 않도록 분리한다. 새 메시지 브로커나 범용 효과 스크립트 엔진은 필요하지 않다.

웹에는 초안, 요청 상태, 작업자와 변경 이력을 저장한다. **실제 적용 버전의 최종 판단은 게임 서버가 한다.** 웹 DB에 적용 요청을 저장했다는 이유만으로 성공 처리하지 않는다.

게임 접속 주소는 서버에 등록한 `serverId`로만 찾는다. 요청에 임의 URL을 넣어 내부 다른 서비스에 접근할 수 없게 한다. 웹과 게임 사이에도 서버별 자격 증명을 사용하며, 검증된 작업자·권한 정보를 위조 방지된 형태로 전달한다. 사용자가 보낸 작업자 이름이나 권한 헤더를 그대로 신뢰하지 않는다.

공개 도감은 기존 30초 동기화를 유지할 수 있다. 관리 화면은 별도의 상태 조회로 적용 결과를 확인한다. 두 경로의 지연을 화면에 구분한다.

### 5.1 필드 정의

게임이 편집 가능한 필드 목록을 제공하고 웹과 AI가 이를 함께 사용한다. 각 필드에는 다음 정보를 둔다.

- 안정적인 필드 ID, 설정 영역, 대상 ID, 한글 이름과 설명.
- 숫자 종류, 단위, 최소·최대, 입력 간격과 반올림 규칙.
- 적용 가능한 시점과 영향을 받는 대상.
- 기본값, 실제 적용값, 예약값, 코드에서 읽는 위치와 검증 상태.

기존 카탈로그의 이름, 빌더 소유권, 티어와 증강 등급은 재사용한다. 숫자 JSON을 탐색해 후보 목록을 만들 수는 있지만, 의미와 적용 시점이 확인되지 않은 키는 읽기 전용으로 둔다. 능력 이름을 보고 범위나 백분율 단위를 자동 추정해 편집 권한을 열지 않는다.

필드 ID에서 내부 설정 키로 변환하는 작업은 게임 코드가 맡는다. API 입력으로 임의 파일 경로나 알 수 없는 JSON 속성을 지정할 수 없게 한다.

## 6. 적용 시점과 게임 규칙

| 모드 | 동작 | 사용 조건 |
|---|---|---|
| `NOW` | 게임 서버의 다음 적용 가능한 틱에 반영 | 요청의 모든 필드가 즉시 적용 허용 목록에 있음 |
| `NEXT_PREPARE` | 전투와 최종 방어가 끝난 뒤, 다음 준비 단계의 초기 처리 전에 반영 | 다음 준비 단계 적용을 검증한 필드만 포함 |
| `NEXT_MATCH` | 현재 경기를 끝내고 새 경기의 설정·선택 상태를 만들기 전에 반영 | 경기 시작에 고정하는 설정 또는 운영자가 선택한 안전한 적용 |

이미 준비 단계가 진행 중이면 `NEXT_PREPARE`는 다음 준비 단계로 예약한다. 예약에 적힌 경기·라운드가 종료되거나 서버가 재시작되면 자동으로 다른 경기의 즉시 적용 요청으로 바꾸지 않는다. 재시작 후 남은 예약은 `재확인 필요`로 돌린다. 아직 경기가 없으면 상태를 재검사한 뒤 새 경기 구성 전에 적용할 수 있다.

현재 전역 `TowerBalanceRuntime`을 재사용하므로 적용 단위는 **게임 서버 인스턴스 전체**다. 같은 프로세스 안에서 특정 플레이어나 특정 테스트 경기만 다른 밸런스로 운영하는 기능은 이 계획에 포함하지 않는다. 테스트 서버와 운영 서버는 별도 인스턴스로 구분한다.

`NEXT_MATCH`를 예약했다고 전역 설정부터 바꾸면 진행 중인 타워 능력이 새 값을 읽을 수 있다. 예약 중에는 현재 런타임과 카탈로그를 유지하고, 지정한 경계에 도달한 뒤 교체한다.

### 기존 상태의 처리

- 공격력 변경은 이후 발생하는 공격에 적용한다. 이미 계산해 예약한 피해, TNT 재폭발, 연사 한 묶음의 피해를 소급 변경하지 않는다. 해당 경로의 고정 여부도 시험한다.
- 체력 변경은 기존 `refreshType`과 빌더별 성장 훅을 사용한다. 체력 비율 유지나 추가 회복 같은 새 규칙을 이번 기능에 끼워 넣지 않는다. 현재 체력의 상한 보정, 준비 단계 회복, 성장형 타워와 회복 불가 방벽을 따로 검사한다.
- 가격 변경은 이후 구매·승급에만 적용한다. 과거 결제액, 판매 투자 장부, 이미 지급한 보상과 성장 점수는 다시 계산하지 않는다.
- 복제본은 기존 생성 시점의 스탯 고정 규칙을 유지한다. 일반 타워 갱신에서 빠지는 임시 복제본까지 일괄 재생성하지 않는다.
- 증강의 선택 결과와 희귀도 순서, 진행 중인 웨이브 편성은 유지한다. 이 값까지 현재 경기에서 바꾸려면 사용자에게 규칙을 확인하고 별도 구현한다.

즉시 적용 가능 범위를 늘릴 때는 필드별 검사와 실제 엔티티 검증을 추가한다. 미검증 필드에 강제 적용 버튼을 제공하지 않는다.

## 7. 검사, 저장, 실패 복구

### 7.1 한 패치를 처리하는 순서

1. 현재 버전과 수정할 필드 목록을 읽는다.
2. 초안에 최종 숫자, 변경 사유, 요청 출처와 적용 모드를 저장한다.
3. 게임이 현재 버전을 기준으로 후보 설정을 만들고 기존 형식 검사와 필드별 의미 검사를 수행한다. 이 단계는 런타임, 파일과 공개 카탈로그를 바꾸지 않는다.
4. 검사 결과에 변경 목록, 경고, 적용 대상 수, 예상 적용 시점과 검사한 내용의 해시를 붙인다.
5. 적용 요청 시 권한, 기준 버전, 초안 해시, 허용 시점을 다시 검사한다.
6. 후보 설정과 변경 이력을 영속 저장하고, 서버 실행 큐에서 적용한다. 예약 요청이면 경계 도달 시 같은 조건을 다시 검사한다.
7. 실제 적용 버전, 시각, 경기와 라운드, 카탈로그 갱신 상태를 반환한다.

한 항목이라도 실패하면 전체 요청을 거절한다. 비용 3개 중 2개만 적용하는 식의 부분 성공은 허용하지 않는다. 효과 설명 미리보기를 위해 전역 런타임을 잠시 교체하는 방식도 사용하지 않는다.

적용 전에 새 카탈로그와 설정을 준비하고, 갱신 대상의 기존 타입·체력·필요한 런타임 상태를 보관한다. 적용은 한 서버 작업 안에서 처리하며 예외가 나면 이전 설정과 대상 상태를 복원한다. 갱신이나 복원 과정에서 구매, 보상, 성장 훅을 다시 발동시키지 않는다. 복원 확인까지 실패하면 신규 변경을 차단하고 운영자에게 알린다. 이 경우 적용 성공으로 기록하지 않는다.

### 7.2 영속 저장 방식

운영자는 파일을 수정하지 않지만, 게임은 재시작 후 같은 값을 읽을 저장소가 필요하다. 초기안은 게임 폴더에 **버전별 불변 밸런스 묶음과 활성 버전 지시 파일**을 두는 방식이다. 기존 원자적 파일 교체 패턴을 재사용한다.

- 최초 전환 시 현재 운영 설정을 읽어 첫 버전으로 등록한다. 번들 기본값으로 덮어쓰지 않는다.
- 밸런스 묶음은 관리 대상 7개 영역과 메타데이터를 담는다. 운영자가 변경한 키만 추적하되, 복구용 원본은 정규화한 전체 설정으로 보관한다.
- 정상 저장과 검사를 마친 묶음만 활성 버전으로 지정한다. 파일 여러 개를 순서대로 덮어쓰는 작업을 원자적 적용이라고 취급하지 않는다.
- 대시보드 관리 모드에서는 이 저장소를 관리 대상 설정의 기준으로 사용한다. 기존 JSON 내보내기는 백업·호환용으로 제공한다.
- 기존 `/semiontd reload`와 수동 파일 변경이 관리 저장소를 우회하지 않도록 한다. 차이를 발견하면 충돌을 표시하고 가져오기 검사를 요구한다. 비관리 설정의 기존 재적용은 유지한다.
- 서버 버전이 올라가 필드 의미가 바뀌면 호환성 검사와 명시적인 설정 마이그레이션을 거친다. 과거 묶음을 새 코드에 강제로 적용하지 않는다.

웹 DB와 게임 저장소를 하나의 트랜잭션으로 취급하지 않는다. 게임은 요청 ID와 최종 결과를 영속 보관하며, 웹은 이 결과를 재조회해 상태를 맞춘다. 중간 단계 저널, 활성 버전 지시 파일과 메모리 버전이 어긋나면 신규 변경을 막고 복구 또는 관리자 확인 상태로 전환한다. 디스크 쓰기 실패, 런타임 적용 예외, 적용 직후 프로세스 종료를 각각 장애 주입 시험으로 검증한다.

### 7.3 충돌과 재시도

- 화면 A와 AI B가 같은 버전에서 출발했는데 B가 먼저 적용했으면 A의 요청을 거절한다. 최신 값과 충돌 항목을 보여주고 다시 검사한다.
- 적용 요청마다 `Idempotency-Key`를 요구한다. 같은 키와 같은 요청은 기존 결과를 반환하고, 같은 키에 다른 내용이면 거절한다. 웹과 게임 양쪽에 같은 키를 전달한다.
- 요청 타임아웃은 실패로 단정하지 않는다. `결과 확인 중`으로 표시하고 원래 요청 ID로 조회한다. 새 ID로 재전송해 두 번 적용하지 않는다.
- 초기 버전은 서버당 미완료 적용 요청을 하나만 허용한다. 초안은 여러 개 만들 수 있지만 예약을 쌓거나 자동으로 재배치하지 않는다.

동시 수정 방지는 강한 ETag와 `If-Match` 비교를 사용한다. 값이 바뀌면 `412 Precondition Failed`로 거절하는 HTTP 의미를 따른다. [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

### 7.4 되돌리기

되돌리기는 이전 숫자를 복사한 새 패치를 만드는 기능이다. 현재 버전과 비교하고 같은 검사·권한·적용 시점을 거친다. 변경 이력을 삭제하지 않는다.

이미 준 다이아, 소비한 재화, 죽은 유닛, 얻은 성장과 지난 전투 결과까지 되돌리지는 않는다. UI에도 `수치만 복원`이라고 표시한다. 공개 카탈로그 내보내기만 실패한 경우에는 전투 수치를 다시 바꾸지 않고 `게임 적용 완료 · 도감 동기화 실패`로 표시해 재시도한다.

## 8. 내부 REST API 초안

관리 API의 공통 접두사는 `/api/internal/v1/balance`다. 공개 `/api/v1/catalog`에 쓰기 기능을 추가하지 않는다. 아래 경로를 구현했으며, 정확한 요청 형식은 [OpenAPI](../../../semion-web/docs/balance-api.openapi.yaml)를 기준으로 한다.

| 메서드·경로 | 용도 |
|---|---|
| `GET /servers/{serverId}/state` | 실제 버전, 대기 요청, 현재 경기, 연결 상태 |
| `GET /servers/{serverId}/fields?domain=&builderId=&q=&cursor=` | 필드 정의와 실제 값 검색. 페이지 단위 응답 |
| `GET /servers/{serverId}/revisions/{revision}` | 기준 설정 묶음과 강한 ETag 조회 |
| `POST /drafts` | 서버·기준 버전·최종 수정값으로 초안 생성 |
| `PATCH /drafts/{draftId}` | 초안 변경. 초안 ETag로 충돌 검사 |
| `POST /drafts/{draftId}/validations` | 무변경 검사, 정규화한 차이와 내용 해시 반환 |
| `POST /servers/{serverId}/deployments` | 검사한 초안의 적용·예약 요청. `202`와 조회 주소 반환 |
| `GET /servers/{serverId}/deployments/{requestId}` | 처리 상태와 실제 결과 조회 |
| `DELETE /servers/{serverId}/deployments/{requestId}` | 아직 적용하지 않은 예약 취소 |
| `POST /servers/{serverId}/rollbacks` | 이전 버전으로 복원하는 새 적용 요청 생성 |
| `GET /servers/{serverId}/history` | 변경 이력과 작업자 조회 |

초안 수정에는 초안 리소스의 ETag를 `If-Match`로 보낸다. 새 적용 요청을 만드는 `POST /deployments`에는 `baseRevision`과 `validationHash`를 넣고 게임 서버가 현재 버전과 비교한다. 다른 리소스에서 받은 ETag를 배포 목록의 `If-Match`로 잘못 사용하지 않는다.

### 요청 예시

아래 숫자는 API 형식을 설명하기 위한 예시이며 밸런스 변경 제안이 아니다. 실제 필드 ID와 허용 모드는 조회 응답에서 가져온다.

```json
{
  "serverId": "production",
  "baseRevision": "balance-0012",
  "reason": "개발자 요청: 방벽 체력 조정",
  "sourceReference": "개발 작업 식별자",
  "applyMode": "NEXT_PREPARE",
  "changes": [
    {
      "fieldId": "tower.augment_folding_barricade.maxHealth",
      "expectedValue": 300,
      "value": 330
    }
  ]
}
```

적용 요청은 `draftId`, `baseRevision`, `validationHash`를 전달한다. 서버는 저장된 초안의 서버 ID와 적용 모드까지 해시에 포함해 검증한다. 초안을 수정하면 이전 검사 결과는 사용할 수 없다.

응답은 `requestId`, `state`, `previousRevision`, `effectiveRevision`, `scheduledFor`, `catalogSyncStatus`를 구분한다. `SCHEDULED`에는 새 실제 버전을 넣지 않는다. 상태는 `VALIDATING → SCHEDULED/APPLYING → APPLIED`를 기본으로 하고, 실패·취소·복구 확인 상태를 따로 둔다.

오류는 인증 실패 `401`, 권한 부족 `403`, 존재하지 않는 대상 `404`, 기준 버전·예약·요청 키 충돌 `409`, ETag 불일치 `412`, 잘못된 값·지원하지 않는 적용 모드 `422`, 요청 제한 `429`, 서버 미연결 `503`으로 구분한다. 오류 본문에 내부 경로, 비밀키나 스택 추적을 내보내지 않는다.

OpenAPI 문서와 테스트 서버 예제를 제공한다. 별도 MCP 서버는 필수가 아니다. AI 도구가 REST 요청을 할 수 있으면 같은 계약을 사용한다.

## 9. 인증과 AI 권한

관리 경로는 내부망이나 VPN으로 제한하고 HTTPS를 사용한다. 게임의 관리 포트를 공개 인터넷에 열지 않는다. 웹이 Docker에서 실행되고 게임이 호스트에서 실행되는 경우 컨테이너의 `localhost`가 게임 서버를 가리키지 않으므로, 배포 전에 비공개 접속 경로와 방화벽을 확인한다.

운영자 로그인은 사용자 결정에 따라 **GitHub OAuth와 운영자 허용 목록**을 사용한다. 허용 목록에는 변경 가능한 사용자 이름 대신 숫자 GitHub 계정 ID를 넣는다. 운영 적용 시 GitHub API로 계정의 2단계 인증 활성화를 확인하며, 확인에 실패하면 적용을 차단한다. 이번 OAuth 로그인에서 MFA 검증을 거쳤음을 증명하는 방식은 아니다. 세션은 NextAuth를 사용하고 자체 비밀번호 시스템은 만들지 않는다.

브라우저에는 게임 서버 비밀키를 전달하지 않는다. 세션 쿠키는 `HttpOnly`, `Secure`를 사용하고, 변경 요청에는 CSRF 방어와 출처 검사를 적용한다. URL 이름에 `internal`이 있다는 이유로 접근 통제를 생략하지 않는다.

| 권한 | 허용 작업 |
|---|---|
| 조회 | 현재 값, 필드 정의, 변경 이력 확인 |
| 편집 | 초안 작성과 검사 |
| 운영 적용 | 지정한 서버와 영역에 적용·예약·되돌리기 |

AI는 서비스 계정과 만료 시간이 있는 단기 자격 증명을 사용한다. 권한에는 서버, 설정 영역, 허용 적용 모드와 변경 한도를 포함한다. 개발자가 해당 범위의 적용 권한을 발급했다면 매번 웹에서 승인 버튼을 누를 필요는 없다. 범위를 벗어난 요청은 추가 승인을 요구한다.

AI 기본 권한은 조회·초안 작성으로 두는 안을 권장한다. 운영 적용 권한은 별도로 발급하고 만료·폐기할 수 있게 한다. 변경 사유에 ‘개발자 요청’이라고 쓴 문장은 권한 증명이 아니다. 실제 작업자는 인증된 계정으로 기록하고, 개발자 요청 기록은 별도 참조 정보로 남긴다.

요청 크기, 항목 수와 호출 빈도에 상한을 두며 임의 코드, 셸 명령과 수식을 실행하지 않는다. 작업 로그에는 인증 토큰과 요청 원문에 포함된 민감정보를 저장하지 않는다. 비공개 관리 경로, 요청별 권한 검사, 감사 기록과 전송 구간 보호는 [OWASP REST 보안 지침](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#management-endpoints)을 기준으로 점검한다.

## 10. 변경 이력과 통계

변경 이력에는 요청 ID, 인증된 작업자, 웹/AI 출처, 서버 ID, 변경 사유, 이전·새 값, 기준 버전, 검사 해시, 적용 모드, 실제 적용 시각과 결과를 남긴다. 같은 내용을 여러 번 요청했는지도 확인할 수 있어야 한다.

경기 도중 패치하면 기존 `catalogVersion` 하나로는 그 경기를 설명할 수 없다. 경기 결과에 시작 버전과 패치 이벤트 목록을 추가하고 이벤트마다 라운드, 서버 틱, 이전·새 버전을 기록한다. 로컬 경기 기록과 웹 동기화는 없는 필드를 허용하는 추가 방식으로 확장한다.

현재 경기의 실제 설정 묶음으로 카탈로그를 생성해야 한다. 타워만 즉시 변경한 경기에서는 그 경기의 증강·웨이브 스냅샷과 새 타워 수치를 묶는다. 다음 경기 예약값은 현재 경기 카탈로그에 섞지 않는다. 미완료 예약이 있으면 먼저 취소해야 다른 적용 요청을 받을 수 있다는 규칙도 유지한다.

웹 통계에서는 경기 중 수정한 경기를 `혼합 버전`으로 표시한다. 초기 버전의 패치별 비교에서는 이 경기를 기본 제외하며 별도 필터로 볼 수 있게 한다. 이를 위해 웹 DB의 관리 이력 저장과 경기 버전 구분에 필요한 추가 스키마가 발생한다. 기존 계획의 ‘DB 변경 없음’을 이 신규 기능에 그대로 적용할 수는 없다. 운영 마이그레이션은 구현 후 별도 승인한다.

## 11. 구현 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1. 읽기 기반 | 실제 설정 조회, 편집 필드 정의, 적용 시점 분류, 내부 연결과 인증 | 웹 숫자가 게임의 실제 적용값과 일치. 알 수 없는 항목은 읽기 전용 |
| 2. 공통 변경 경로 | 초안 검사, 버전 충돌, 중복 요청 방지, 버전 저장, 다음 경기 적용, 복구 | 유효하지 않은 변경이 런타임과 파일에 영향을 주지 않음. 재시작 후 적용 버전 유지 |
| 3. 운영자 편집기 | 검색, 표 편집, 일괄 증감, 변경 미리보기, 예약, 이력, 되돌리기 | 파일을 열지 않고 타워·증강 변경과 복원을 완료 |
| 4. AI 적용 | 서비스 계정, 범위 제한, OpenAPI, 동일 변경 경로 연결 | 권한 있는 개발자 요청만 적용. 재시도에도 한 번만 반영 |
| 5. 경기 중 적용 | 허용한 타워 수치의 즉시·다음 준비 단계 반영, 혼합 버전 기록 | 기존 타워·새 타워·승급·복제본의 규칙과 기록이 일치 |

최종 범위에는 5단계까지 포함한다. 2단계만 끝내고 ‘AI가 진행 중인 전투를 즉시 바꿀 수 있다’고 안내하지 않는다. 증강과 웨이브의 현재 경기 강제 변경은 이 범위와 별도로 결정한다.

`BalanceChangeService`에서 기존 타입·가격·설명 갱신 코드를 재사용한다. `SemionGameManager.configure` 전체를 호출하거나 임시 파일 수정 후 `/reload`를 실행하는 방식으로 대체하지 않는다. 순수 후보 검사와 실제 적용을 분리해 검사 중 전역 상태 변경을 막는다.

웹은 기존 Next.js와 PostgreSQL을 확장한다. 인증 연동 외에 새 대시보드 프레임워크, 메시지 브로커, 독립 AI 서버를 전제로 두지 않는다. 필드 단위의 의미·검증 정의와 경기 상태 보존이 가장 큰 작업량이다.

## 12. 검증 계획

### 필수 자동 검사

- 유효 숫자, 경계값, 틱·백분율 변환, 정수 반올림, 공유 능력의 영향 대상.
- 등록하지 않은 키, 타 서버, 권한 밖 영역, 만료·폐기된 자격 증명, CSRF 요청 차단.
- 같은 버전의 동시 편집, 초안 검사 뒤 수정, 예약 대기 중 버전 변경, 중복 요청 키와 재시도.
- 검사 단계에서 파일·런타임·카탈로그가 바뀌지 않는지 확인.
- 디스크 쓰기 실패, 부분 적용 예외, 응답 유실, 서버 재시작, 웹 DB 장애와 카탈로그 내보내기 실패.
- 공격력·사거리 갱신, 체력 감소·증가, 빌더 성장 유지, 승급·판매 장부, 회복 불가 방벽, 임시 복제본 유지.
- 준비 단계 시작과 패치 적용이 같은 틱에 겹치는 경우, 최종 방어 중 예약, 경기 종료 직후 예약 처리.
- 진행 중인 증강·웨이브 스냅샷 유지, 다음 경기 적용, 혼합 버전 경기의 저장·동기화·통계 구분.

게임은 집중 검사 후 Java 21로 `rtk ./gradlew test runGameTest remapJar --console=plain --no-daemon`을 실행한다. 웹은 테스트, 린트, 타입 검사, 운영 DB와 분리한 빌드와 임시 PostgreSQL 검사를 수행한다.

### 실제 화면과 운영 경로 검사

테스트 서버에서 운영자 편집 → 검사 → 적용 → Minecraft 타워 상세와 실제 전투 변화 → 웹 상태 확인 → 되돌리기를 한 번의 흐름으로 검증한다. 같은 변경을 AI API로도 실행해 결과가 같은지 확인한다.

현재 사용하는 Fabric 1.21.8 클라이언트 검수 도구로 표시와 전투 효과를 확인한다. 자동 검사, 실제 브라우저 조작, Minecraft 화면 검증을 별도로 기록한다. 30명 접속 시험은 다시 요구하지 않는다. 대신 대표적인 일괄 변경에서 서버 틱 지연과 웹 응답 시간을 측정한다.

## 13. 구현 전에 결정할 사항

| 결정 | 권장안 | 다른 선택의 영향 |
|---|---|---|
| 일반 운영 패치의 기본 시점 | 다음 경기. 검증된 타워 긴급 수정만 즉시·다음 준비 단계 선택 | 현재 경기 수정이 기본이면 혼합 버전 경기와 플레이 중 규칙 변경이 잦아짐 |
| 증강·웨이브의 진행 중 경기 변경 | 기존 스냅샷 유지, 다음 경기 적용 | 즉시 변경하려면 선택 효과, 예약 소환, 회복 횟수, 이미 편성한 웨이브의 이관 규칙부터 확정해야 함 |
| 운영자 로그인 | 확정: GitHub OAuth + 숫자 계정 ID 허용 목록, 운영 적용 시 계정 2단계 인증 확인 | OAuth 앱 등록과 운영 계정 로그인을 배포 전에 확인 |
| AI 운영 권한 | 기본은 초안. 개발자가 필요할 때 단기 적용 권한 부여 | 상시 운영 적용 권한은 만료·영역 제한과 사고 대응 책임을 더 엄격히 정해야 함 |
| 공개 후보·빌더 활성화 | 이번 수치 편집기에서 제외 | 포함한다면 수치 패치와 구별하는 별도 권한·확인 화면 필요 |

기획 승인 후에는 테스트 환경에서 구현한다. 운영 포트 개방, 인증 자격 증명 발급, 운영 DB 마이그레이션, 라이브 파일 관리 방식 전환과 최초 운영 패치는 별도 승인 대상으로 남긴다.

## 14. 이번 검토의 산출물과 한계

최초 기획 검토에서는 재사용 경로, 적용 시점 차이와 신규 작업을 확인했다. 이후 사용자가 구현, 프런트엔드 작업, GitHub 인증과 담당별 병렬 작업을 승인했다. 문구는 stop-slop과 한국어 문법 기준으로 정리한다.

## 15. 구현 결정 기록

- 게임의 비공개 경로는 `/internal/balance/v1`, 웹 경로는 `/api/internal/v1/balance`다. 게임은 루프백에서만 수신한다. 운영 내부망 연결은 별도 배포 작업이다.
- 필드 ID는 `영역:/JSON/포인터`를 사용한다. 예: `tower:/towers/t1_pig_tower/damage`. 위 8절의 점 구분 ID는 최초 계약 예시이며 실제 요청에는 조회한 필드 ID를 사용한다.
- 초기 즉시 적용 허용 목록은 동물 빌더 타워다. 다른 타워는 다음 경기부터 적용한다. 알 수 없는 능력 수치는 읽기 전용으로 둔다.
- 관리 저장소는 `config/semion-td/balance-management/`다. 불변 버전 파일과 활성 버전·요청 결과를 원자적으로 교체하는 인덱스를 사용한다. API 비활성화 후에도 기존 관리 저장소가 기준이다.
- 재시작 시 미완료 요청은 재확인 상태로 유지한다. 원래 JSON을 수동 수정했는지는 최초 등록 버전과 비교한다. 관리 저장소 복구에 실패하면 구형 JSON으로 경기 시작을 진행하지 않는다.
- GitHub 계정 ID 허용 목록과 암호화 세션, CSRF·출처 검사, 서버별 HMAC 서명, 만료·폐기 가능한 범위 제한 AI 토큰을 사용한다.
- 첫 등록 시 기존 설정을 읽고, 운영 설정을 번들 기본값으로 덮어쓰지 않는다. 공개 후보·직업 활성화도 편집 대상에서 제외한다.
- UI별 의미, 사용 순서와 환경 변수는 [웹 운영 안내](../../../semion-web/docs/balance-dashboard.ko.md), API 계약은 [OpenAPI](../../../semion-web/docs/balance-api.openapi.yaml)에 기록한다.
